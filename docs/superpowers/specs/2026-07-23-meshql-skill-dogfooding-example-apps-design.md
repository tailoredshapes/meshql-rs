# Building four real products on meshql, overseen to harden the skill suite along the way

**Date:** 2026-07-23 (revised same day — see "Revision history" below)
**Status:** Approved design, pre-implementation
**Depends on:** `meshql-iron` installed and validated in `meshql-rs`, `meshql`, `meshobj` (`docs/superpowers/specs/2026-07-23-meshql-iron-skill-design.md`, complete) — including its own previously-open item, honesty-field parity (`X-Meshql-Created-At`/`createdAt`) on the Java and TypeScript backends, which was independently confirmed present on both during that project (see that spec's implementation notes). `meshql-patterns` and `merkql-architecture` are now installed in all three backend repos (this project's own Phase 0, complete).
**Unblocks:** nothing downstream yet.

## Motivation

**These are real products, not example apps.** CMS, Twitter Clone, Asset Management, and CRM are meant to be actually-usable services, each living in its own dedicated repository — not demonstrators sitting in an `examples/` folder whose job is just to prove a pattern works. This is a correction to the project's original framing, which treated the four builds as disposable test harnesses with product quality as an optional bonus; that framing was wrong and is fully superseded by this revision (see "Revision history").

That said, the reason this project sits under `meshql-rs`'s `docs/superpowers/` and follows the skill-dogfooding process at all is still real and still matters: building four genuinely different products is also the best available test of whether the meshql skill suite (`meshql-patterns` for backend authoring, `meshql-iron` for frontend consumption, `merkql-architecture` for cross-language event-pipeline reasoning) is *sufficient*, on its own, for an LLM agent to build something real without additional hand-holding. The oversight-and-patch loop from the original design — review each build against the actual skill content, patch what's missing or wrong, verify the patch with a fresh independent build — stays exactly as important as before. It's just no longer the *only* thing that matters; a good product that happens to validate the skill is the actual goal now, not a good validation run that happens to produce a usable product.

## Non-Goals

- **Pre-designing each product's technical architecture** (entity model, event/domain split, which entities get workers). Doing this myself before dispatching a builder agent would hand it the exact reasoning that's supposed to be under test. The builder agent still derives its own architecture from the skill suite — what's changed is that it now does so against a real, detailed *product* brief (target users, feature set, "done" criteria) instead of a one-sentence prompt. Business requirements are now rich; technical design is still the builder's own job.
- **Cloud-native ports of the worker/queue layer (AWS/Azure).** Explicitly future work, not part of this project. Per the user: only the worker + queue implementation should need to change when that day comes ("porting the workers from merkql to cloud native techs") — the event/domain-mesh shape of each app shouldn't need to change at all. Nothing in this project should be built in a way that makes that future port harder, but building it now is out of scope.
- **Building import/interop tooling for the reference product a domain is grounded in** (e.g. a WordPress importer for the CMS). Grounding the domain model in an existing product's shape is meant to make this kind of thing a natural, low-effort future addition (a real import is "just an event stream a worker folds into the domain," per the user) — but building the importer itself is not part of this project's first pass.
- **Building all four products in every language (12 builds).** Rejected as scope explosion relative to the actual goal. One language per product, with a Rust `merkql` sidecar where the product's main language isn't Rust, gives real cross-language coverage of all three `meshql-iron`/`meshql-patterns` installations at 4x cost instead of 12x.

## Revision history

This spec was originally written and approved with the four builds framed as disposable validation harnesses (`examples/cms` etc., inside the `meshql-rs`/`meshql`/`meshobj` repos, one-sentence briefs, "starter-kit quality is a welcome byproduct, not the goal"). Phase 0 (porting `meshql-patterns`/`merkql-architecture`) and a first pass at Phase 1 (CMS) were completed under that framing — see `docs/superpowers/plans/2026-07-23-meshql-skill-dogfooding-example-apps.md` for that execution history, including a real skill gap it surfaced and fixed (a precedence conflict between `meshql-iron`'s consumer-facing "don't force event-sourcing" language and `meshql-patterns`' design-time guidance — see the `domain-design.md`/`event-vs-domain-mesh.md` commits from that session). The user then corrected the framing: these are meant to be real products in dedicated repos, not examples, with richer product briefs, real Casbin-backed roles, and domain models built via an actual event-storming pass (now taught directly in `domain-design.md`) grounded in an existing real-world product's domain shape rather than invented from scratch. The CMS work-in-progress from the original framing was explicitly discarded (not ported forward) per the user's direction, and Phase 1 restarts clean under this revision. Phase 0's skill installations remain valid and are not redone.

## Prerequisite (complete): port `meshql-patterns` and `merkql-architecture` to `meshql` and `meshobj`

This section is retained as the record of why Phase 0 was necessary and how it was scoped; the work itself is done (see "Depends on" above).

Checked directly: only `meshql-rs/.claude/skills/` has `meshql-patterns` and `merkql-architecture`; `meshql/.claude/skills/` and `meshobj/.claude/skills/` have only `meshql-iron`. For the two apps assigned to those repos (Twitter Clone, Asset Management — see below), a builder agent would have frontend-consumption guidance but *nothing* teaching it the backend event/domain-mesh pattern or the `merkql` cross-language constraint. That's not a fair test of the skill suite; it's a test of a skill that doesn't exist there yet. Both apps also need `merkql-architecture` specifically, since both require a Rust `merkql` sidecar per the "Merkql scope" decision below.

**This is a bigger lift than porting `meshql-iron` was.** `meshql-iron` is language-agnostic by construction — it teaches consuming HTTP surfaces (manifest, REST, GraphQL), not how a server is wired, so its three installations are near-identical modulo two citation lines. `meshql-patterns` teaches *authoring* a backend, and its content is inherently Rust-specific: real code (`RootConfig::builder()`, `Arc::new(MongoRepository::new(...))`), real file paths (`meshql-core/src/lib.rs`), and a fluent builder API that Java and TypeScript don't share verbatim. Porting it means preserving the architectural content (the six invariants, the domain-design methodology, the decision guide, the anti-patterns) while replacing every code example with that language's actual wiring shape — closer to writing two new skills using `meshql-patterns` as a structural template than to a copy-and-patch job.

**Known head start, to confirm and use during implementation, not fully resolve here:** both `meshql/CLAUDE.md` and `meshobj/CLAUDE.md` already contain substantial backend-authoring documentation for their own languages (`meshql/CLAUDE.md` has a full "MeshQL Integration Guide for AI Agents" section — Envelope shape, `RootConfig`/`QueryConfig` records, resolver configs, storage configs, GraphQL schema pattern, REST endpoint table, honesty headers, common patterns, anti-patterns, all in Java; `meshobj/CLAUDE.md` is 298 lines covering its own Lerna/Yarn-based structure). These should be read closely and adapted into proper `.claude/skills/meshql-patterns/` installations rather than written from scratch — likely most of the real content already exists, just not packaged as an auto-loading Skill with the invariant-first structure `meshql-patterns` uses. Confirming how much of each CLAUDE.md transfers directly is implementation work, not something to pre-solve in this spec.

Both ports get `merkql-architecture` too — that skill's content (the embedded-library constraint, the "connector + worker must be Rust, projection can be any language" rule) is language-agnostic prose about an architectural boundary, not language-specific code, so it should port far more like `meshql-iron` did: near-verbatim, no restructuring needed.

## Merkql scope: every app uses merkql, via a Rust sidecar where the app isn't Rust

Confirmed against `merkql-architecture`: merkql is an embedded Rust library, not a network service. Two pieces touch it directly and must be Rust — the storage connector for the event meshlette, and the worker that reads events off it. What the worker writes to (the projection's REST surface) is language-agnostic, since that's a plain HTTP call.

Decision (user-confirmed): **every one of the four apps uses merkql for its event→worker→domain slice**, not just the Rust ones. For Twitter Clone (TS) and Asset Management (Java), this means the event meshlette + worker are a small Rust process/crate (living in that app's own directory, or wherever the builder agent judges appropriate), while the domain projection it writes to — and everything else in the app — stays in the app's assigned language. This is a real, deliberate test of the exact cross-language composition `merkql-architecture` exists to describe, not an edge case to avoid.

## The four apps: assignment and build order

| Order | Product | Backend language / sidecar | Why this pairing |
|---|---|---|---|
| 1 | CMS | Rust | Draft → revise → publish maps naturally onto event-mesh; fully Rust, no cross-language complexity — establishes the baseline loop cheaply. |
| 2 | CRM | Rust | Mixed-mode test: contacts/companies are plain CRUD, an activity/interaction log naturally event-sources into an engagement-score-style projection. Still fully Rust — validates the "don't force event ceremony onto plain CRUD entities" guidance before adding cross-language difficulty. |
| 3 | Twitter Clone | TypeScript + Rust merkql sidecar | Tweets are naturally create-only events; feeds/timelines are projections — same pattern as CMS/CRM, different domain, first cross-language build. |
| 4 | Asset Management | Java + Rust merkql sidecar | Mostly CRUD (assets, categories, locations) with an assignment/checkout event feeding an availability projection — second cross-language build, benefits from whatever the Twitter Clone build taught about the sidecar pattern. |

Order is a deliberate complexity ramp: prove the oversight loop mechanics on pure-Rust products first (cheap iteration, no sidecar composition to debug), then take on cross-language composition once the skill content from rounds 1–2 has already been hardened.

## Deliverable location and cross-repo dependency

Each product is a **new, dedicated top-level repository** under `/tank/repos/tailoredshapes/` — `cms`, `twitter-clone`, `asset-management`, `crm` — not a folder inside `meshql-rs`/`meshql`/`meshobj`. This is a real repo per product: its own git history, its own README, deployable on its own.

This introduces a real technical wrinkle the original (in-repo `examples/`) framing didn't have: a standalone repo can't use path dependencies (`meshql-core = { path = "../../meshql-core" }` only resolves inside the `meshql-rs` workspace). Per this project's own established convention for cross-repo Rust dependencies (git deps pinned to a tag or commit — see how `merkql`/`merksql` are consumed today), each product's backend depends on its language's meshql implementation the same way: `meshql-core = { git = "https://github.com/tailoredshapes/meshql-rs", tag = "..." }`-style entries, not path deps. `meshql-rs` doesn't currently have version tags cut for its own crates (only `merkql`/`merksql`, which it depends on, are tagged) — cutting a tag (or pinning to a commit SHA if a tag isn't warranted yet) is part of setting up the first product's repo, not assumed to already exist. The Java and TypeScript products need the equivalent for their ecosystems (Maven coordinates / npm package resolution against `meshql`/`meshobj`) — confirm the actual mechanism each language's package manager expects during that product's setup, since Maven/npm cross-repo consumption conventions differ from Cargo's git-dependency support and shouldn't be assumed identical.

## Per-app process

**1. Product brief.** Unlike the original one-sentence prompt, each product now gets a real brief before the builder agent is dispatched: target users, core feature set, explicit non-features, and "done" criteria — written up and reviewed with the user first, the same way this spec itself was. The brief describes the *product*, not the *architecture* — it does not name entities, does not decide the event/domain split, and does not pre-empt the event-storming pass below. Two requirements apply to every product's brief:

- **Ground the domain in an existing, real product's actual shape** rather than inventing one from scratch — research how an established product in the same space actually models its domain, and adapt that shape (not its code). This also sets up realistic future interop for free (per `domain-design.md`'s replay-from-history section): importing real data from the reference product becomes "feed its history through the event mesh and let the existing worker fold it," not a bespoke importer — a benefit worth having even though building that importer is explicitly out of scope for this pass (see Non-Goals).
- **Real Casbin-backed roles**, not `NoAuth`. The event-storming pass (below) identifies actors; those actors become real roles wired via `CasbinAuth`/the language-appropriate equivalent, not left implicit.

**2. Event storm, as a real artifact.** Per `domain-design.md`'s new "Run an actual event storm" section (added during this project, see Revision history): before wiring any code, the builder agent produces a written event-storming artifact — domain events, commands, actors, policies, aggregates, read models, and explicitly-flagged hotspots — grounded in the reference product identified in the brief. That artifact is then converted into meshlettes and workers using the mapping table `domain-design.md` now documents (events → event meshes, policies → workers, read models → projections, actors → Casbin roles).

**3. "Fully formed" bar.** A real, usable v1 of the product described in its brief — not a 3-entity toy proving the pattern works. Concretely: the full feature set from the brief's "done" criteria, real Casbin-backed authorization tied to the storm's actors, the event/domain-mesh architecture the storm's policies imply (not necessarily every entity — plain CRUD is still correct where the storm doesn't surface a policy for it), a working frontend (vanilla per this project's standing frontend conventions, built using `meshql-iron`), and passing tests. Horizontal scalability is not separate work — it's inherent to the architecture (invariant 6) as long as nothing violates it.

**4. My review.** After each build, I read the actual artifacts — not just the agent's self-report — looking specifically for: whether the event storm artifact itself is sound (not just whether the code matches it); places it had to guess because a skill was silent or ambiguous; places it got the event/domain split wrong or right for the wrong reason; places it hit a real bug; places the cross-language sidecar composition (products 3–4) went differently than `merkql-architecture` implies; whether the domain grounding (requirement in step 1) actually reflects the reference product or is superficial.

**5. Skill patch.** Findings become direct edits to the relevant skill doc(s) — `meshql-iron`, `meshql-patterns`, or `merkql-architecture`, in whichever repo(s) are affected — plus a regression test where the finding was an actual code bug rather than a documentation gap. This follows the same lightweight pattern already used in this project (the `examples/farm` template-bug fix, the `domain-design.md`/`event-vs-domain-mesh.md` precedence fix): no full brainstorming cycle per finding, just a direct fix with a test or verification proving it, committed on its own. If a finding invalidates a build already in progress (as the precedence gap did for the first CMS attempt), redo that build against the patched skill with a **fresh, zero-context agent** — reusing the same agent proves nothing, since it already knows the "right answer" from being told. Watch for contamination when redoing a build: a fresh agent that stumbles onto a prior (possibly flawed) attempt sitting in a sibling worktree/branch may reuse it instead of designing independently — this happened once already; prior attempts should be moved out of casual discovery range (or the agent explicitly told not to reuse them) before a clean retry.

**6. Move to the next product.** Sequential, not parallel, specifically so patches from product *N* are already in place before product *N+1*'s builder agent starts — the whole value of the oversight loop is that the fourth product should need far fewer skill corrections than the first.

## Validation

Two things are being validated now, not one — the product has to actually be good, and the skill suite has to actually be sufficient. On the skill side, success isn't a fixed pass/fail gate, it's a trend: each product's review (step 4 above) should surface fewer *new* categories of skill gap than the one before it, especially between products 1→2 (same language, should be nearly clean by product 2) and 3→4 (both cross-language, product 4 should reuse product 3's sidecar-composition lessons rather than rediscovering them). If product 4 still surfaces first-time-seen gaps as large as product 1's, that's a signal the skill content isn't generalizing and is worth a harder look. On the product side, "done" is whatever that product's own brief says it is — judged against the brief, not against the other three products.

## Summary of what this design intentionally leaves open

- **Cloud-native worker ports (AWS/Azure)** — explicitly future work, not touched here.
- **Import/interop tooling for the domain a product is grounded in** (e.g. a real WordPress importer) — the architecture is meant to make this cheap later, but building it isn't part of this pass.
- **The exact cross-repo dependency mechanism for the Java and TypeScript products** (Maven/npm equivalents of Cargo's git dependency) — flagged as a real question in "Deliverable location," not resolved here.
- **Whether Phase 0's now-complete `meshql-patterns`/`merkql-architecture` installations need any further revision beyond the event-storming and precedence fixes already made** — possible but not assumed; future product builds may surface more.
